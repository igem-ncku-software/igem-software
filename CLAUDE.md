# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

LasReader (iGEM NCKU-Tainan 2026): a frontend/backend-split web app for the team's wet-lab data tools (the plate reader assay, and the CAPTURE-Screen fluorescence-reader UI). The CAPTURE-Screen reader connects itself to the backend and every hardware page reaches it through the backend; calibration-plan and curve persistence still run in the browser. There is no simulated device anywhere (see the hardware notes below). The two halves deploy independently and talk over HTTP/CORS and WebSocket — there is no shared build step, monorepo tooling, or shared types.

- `frontend/` — static HTML/CSS/vanilla JS, no framework, no bundler. Deployed as-is to GitHub Pages.
- `backend/` — FastAPI app. Deployed to Render at `https://igem-ncku-software.onrender.com`.
- `scripts/` — install and run scripts, `.sh` and `.ps1` versions of each.

## Commands

### Scripts (from the repo root)

```bash
bash scripts/setup.sh    # create backend/.venv + pip install
bash scripts/dev.sh      # backend on :8000 and frontend on :5500 together
```

PowerShell equivalents are `scripts\setup.ps1` / `scripts\dev.ps1`. Both `dev` scripts run the frontend static server in the background and **uvicorn in the foreground on purpose** — Ctrl+C then reaches uvicorn directly, and the script's exit handler stops the frontend. Backgrounding both instead leaves orphaned servers holding the ports, because a background shell on Windows never receives the interrupt.

The `.ps1` files must stay **UTF-8 with BOM**. Windows PowerShell 5.1 decodes a BOM-less `.ps1` as system ANSI, which mangles the Chinese comments into a parse error.

### Backend (from `backend/`)

```bash
# setup
python -m venv .venv
.venv\Scripts\activate        # Windows
pip install -r requirements.txt

# run dev server (reload on change)
uvicorn app.main:app --reload

# tests
pytest
```

Because `main.py` lives inside the `app` package, it must be run as `app.main:app` — running `python main.py` or `uvicorn main:app` directly will fail.

`backend/tests/` has 43 tests as of the last run: `tests/swarming/` (the upload's refusals through `TestClient`; no analysis test until the team supplies an original plate photo — real data only), `tests/plate_assay/` (empty but for `__init__.py`: the assay runs in the browser, see below), `tests/hardware/` (`test_hub` drives `DeviceHub` directly through a fake connection; `test_router` goes through `TestClient`; device messages live in `payloads.py`), and `tests/live/` (the same split for `LiveHub` and `WS /api/live/spectrum`, reusing `tests/hardware/payloads.py`). `tests/conftest.py` puts `backend/` on `sys.path`, so `pytest` must be run from `backend/`. The hardware router tests hold two sockets (or a socket and an HTTP call) at once, so they enter the `TestClient` as a module-scoped context manager; otherwise each connection runs on its own event loop and the hub's asyncio queues and futures break.

### Firmware (from the repo root)

```bash
arduino-cli compile --fqbn esp32:esp32:esp32doit-devkit-v1 firmware/capture_screen
```

Compiles cleanly (warnings only from inside the libraries) against ESP32 core 3.3.8, DFRobot_AS7341 1.0.0, Adafruit SSD1306 2.5.17, Adafruit GFX 1.12.6, Adafruit BusIO 1.17.4, ArduinoJson 7.4.3, and WebSockets 2.7.2. The build needs `firmware/capture_screen/secrets.h` to exist (the sketch `#error`s without it). The Arduino IDE ships its own `arduino-cli.exe` under `resources/app/lib/backend/resources/` in its install folder, so no separate install is needed; pass `--build-path` somewhere outside the repo. Flashing is done by the user.

### Frontend

No build step. Serve the folder with any static server (e.g. `python -m http.server 5500`, or VS Code Live Server — port 5500 is already whitelisted in CORS). Opening the files via `file://` mostly works, but the pages will hit the Render backend rather than a local one, since `config.js` branches on hostname — and the landing page's **live spectrum will not connect**, because a `file://` page's `Origin` is the string `"null"`, which `WS /api/live/spectrum` rejects like any other unlisted origin.

## Architecture

### Plate Reader Assay

On 2026-09-28 the user cleared the old dose-response feature and renamed it **Plate Reader Assay** (files and paths too, `plate-assay` / `plate_assay`), because its output is a sample's inferred AHL, not a strain's characterization — "dose-response" conventionally means the latter, and CAPTURE-Screen already calls the same workflow a calibration. The old pipeline (SpectraMax ASCII parser, `experiment.yaml` plate map, time logistic, Hill fit) survives in git history.

What was built the same day, as designed with the user (they chose a list table over a plate grid, to be independent of any instrument):
- **A one-off calculator, in the browser only.** Standards and samples read together are typed or pasted into one table; nothing is stored, the curve serves only the readings entered with it (a plate reader's signal scale changes with instrument, gain and day, so in-plate standards are what makes it instrument-independent), and the CSV is the record. `beforeunload` asks before leaving unexported data. `/api/plate_assay` stays mounted with no endpoints and `tests/plate_assay/` stays empty; numpy, scipy, pandas, lmfit, PyYAML and python-multipart stay in `requirements.txt` (the user's choice).
- **Four step cards**, states derived from the table and the fit: 1 Enter data (experiment: date, strain, detection required — the field is labelled Detection on the page, since "signal" there also names the fitted number, but is still `signal` in code; instrument, notes optional — recorded, never computed with) → 2 Fit (standards table with exclusions and a required reason, Fit button, curve, EC50 / Hill / LOD / RMSE tiles) → 3 Results ("Inferred AHL") → 4 Export (CSV + curve PNG). Step 1 incomplete holds every later step, even with a fit.
- **The table** (the one internal format; typed, pasted, or filled from the plate import): one row per standard concentration (nM; 0 = blank, cells without AHL; rows with the same concentration merge) or sample (unique name, case-insensitive, and a dilution ≥ 1), 3 replicate columns by default, 1–6. A row with nothing typed is ignored. A block pasted from Excel fills from the target cell right and down (columns: role, concentration/name, dilution, reps), adding rows and replicate columns. Every problem is listed at once, grouped by kind, like Calibrate's manual table. Any change to a standard discards the fit; a sample's cells and the experiment fields don't (results are recomputed from the table on every render). Numbers with comma thousands separators in groups of three ("12,345", as Excel copies a formatted cell) are accepted; any other comma is not a number.
- **Results**: a sample's replicates are averaged and converted once (reading variance / n), shown in the well and × dilution in the sample, with CV but **no CV threshold** (none until real data says what's normal). Outside the usable range only the bound is shown.
- **CSV**: one row per reading, excluded ones with their reason, with the curve and the sample's result beside each row; full precision, CRLF + BOM.
- **OD normalization** (added 2026-09-28 at the user's request, after wet lab mentioned OD): a radio switches the signal between Fluorescence and Fluorescence ÷ OD600. With it, each replicate is an F column and an OD column from the same well (F 1–n, then OD 1–n; the OD columns are tinted), a third role **Medium blank** (medium only, no cells) appears, and every well's signal is `(F − mean medium F) / (OD − mean medium OD)`. Required then: at least one medium replicate with both values, both values for every replicate, and every OD above the medium's (else F/OD is undefined — listed by row). The first switch adds an empty medium row at the top; OD cells are kept while the mode is off, and a medium row left in Fluorescence mode is a problem rather than silently ignored. A medium blank's cells discard the fit (they enter every standard). Paste maps F then OD columns and, in OD mode, never adds replicate columns (that would move the OD block). The fit table shows F and OD beside the signal; the axis says "÷ OD600, less medium blank (a.u.)"; the CSV carries `normalization`, `medium_f_mean`, `medium_od_mean`, `fluorescence`, `od600` and `signal` (the number fitted or converted), with medium rows included. The medium-blank subtraction is the common practice, **not yet confirmed against how the team's wet lab does it** — check with them before relying on it.
- **Import from a plate** (`js/plate_layout.js`, added 2026-09-28 at the user's request): the goal is that **other iGEM teams use this team's biosensor on their own plate readers**, and every reader exports an 8 × 12 block. A `<details>` in step 1 takes the pasted fluorescence plate (and the OD600 plate with F/OD), with or without row letters / column numbers, tab-, comma- or space-separated; a 96-well map where wells are selected (click, Shift-click range, row / column headers) and marked Standard (nM) / Sample (name, dilution) / Medium blank / Clear mark; and "Fill the table (replaces it)". It is an importer, not a second format: it builds the list table (one row per concentration / sample / medium, its wells as replicates in plate order, at most `ASSAY_MAX_REPS`), and everything after reads the table. Rows remember each replicate's well (`row.wells`), shown as the reading's label in the fit table and as the CSV's `well` column; editing that value by hand clears it. Fill lists every problem at once (empty or non-numeric marked wells, a sample with two dilutions, too many wells in a group, medium without F/OD). Non-numeric reader tokens (e.g. `OVRFLW`) are reported as not a number; recognising them as saturation was deferred.
- **Decided for v1** (my recommendations, accepted): nM only, no heatmap, no stored history. Those, multiple strains per page, a protocol template and reference EC50 / Hill check from the wet lab's validated data (EC50 and Hill are in concentration units, so they should carry across instruments), and a CAPTURE-Screen ↔ plate-reader cross-validation are candidates for later — the template and reference values must come from real wet-lab data, never simulated.
- **The math is `js/curve_fit.js`'s `CurveFit`**, the same code CAPTURE-Screen's `fitCurve` calls — moved out of `hardware_local.js` unchanged on 2026-09-28. Don't give the assay its own fit.
- The page loads `config.js`, `curve_fit.js`, `plate_assay.js`, `plate_layout.js`, `backend_status.js` — not `hardware_common.js`, which starts the hardware step bar and device polling; `plate_assay.js` keeps its own copies of the few formatting and step-card helpers. Page text says "infer", never "quantify".

The team's real data is **SoftMax Pro `.sda` documents from a SpectraMax M3** (binary). The user set `.sda` aside for now; reading it directly would be one more input converter feeding the same table. What was found in two real files (`20260810 time-course fluorescence.sda`, `20260831 pyocyanin.sda`): each read is its own Plate section (endpoint reads repeated by hand, not kinetic mode), with its own `Start Read` time written in a zh-TW locale (`下午 05:23 2026/8/10`); each plate's 96 values are a contiguous little-endian float64 array, NaN for unread wells; absorbance and fluorescence (Ex 460 / Em 530) sit in separate experiments, read at different times and different counts.

### Cross-Validation

`compare.html` + `js/compare.js` (added 2026-09-28 at the user's request, as its own page): the same samples inferred on a plate reader and on CAPTURE-Screen, compared — the evidence that the team's own reader agrees with a commercial one. Four step cards: 1 Plate reader (a Plate Reader Assay CSV, file input; its `ahl_sample_nM`, i.e. × dilution, is compared), 2 CAPTURE-Screen (a Measure batch from this browser via `HardwareApi.listBatches()` / `getBatch()` — read only — or a batch CSV from another computer, plus one "dilution before reading" for all its samples, since batches carry none), 3 Comparison, 4 Export (CSV + PNG). Nothing stored; `beforeunload` asks until exported.
- Samples pair **by name, case-insensitive**; names on one side only are listed, and a strain mismatch is warned about (not blocked). Nothing a side can't compare is dropped silently (found in a self-review, 2026-09-28): Measure keeps `Lake A` and `lake a` as two samples, so a case-only collision is reported and only the first compared; a result marked `ok` without a usable number and CI (a hand-edited CSV) is shown as "Invalid" and left out, rather than turning every statistic into NaN; an unfinished browser batch is warned about, since its results can still change. Each side's problems appear in its status line and in the comparison's warning. Limits of agreement from exactly 2 pairs say "Rough: only 2 pairs". Export filenames use the local date, not UTC.
- **Only pairs with a number on both sides enter the agreement**: a bound ("< LOD", "> range") shows in the table but is never a value. Agreement is on the log scale (errors are proportional, values span decades): geometric mean ratio CAPTURE-Screen ÷ plate reader, Bland–Altman 95% limits of agreement on log10 ratios (needs ≥ 2 pairs), and how many pairs' 95% CIs overlap. **No pass/fail threshold** until real data says what agreement to expect.
- The plot is log-log with both CIs as bars and a dashed y = x.
- The page loads `hardware_processing.js`, `curve_fit.js`, `hardware_local.js`, `hardware_api.js` to read batches, but not `hardware_common.js` (no step bar or polling); it keeps its own small helpers, like `plate_assay.js`.
- Entry points (the user's "direction 3"): on the landing page the Plate Reader Assay and CAPTURE-Screen cards stay side by side as they were, and the Cross-Validation card sits centred below them at one column's width, joined by `.nav-bridge` — a line down from the middle of each card, meeting in one arrow down to it (the user's layout, 2026-09-28, after rejecting the card placed between the two). Below 720 px the cards stack and the bridge is one short arrow. Also a one-line link from the Export step of both the Plate Reader Assay and Measure.
- It reads both CSVs by column name, so **renaming a column in either export breaks it** — `requireColumns()` then says which. The Plate Reader Assay CSV's experiment text is `signal_description`, not `signal` (renamed 2026-09-28: the file had two `signal` columns, and `signal` is the fitted number).

### Swarming Assay

`swarming.html` + `js/swarming.js` + `backend/app/swarming/` (added 2026-10-08 at the user's request): the team's colony-measurement notebook `iGEM_cv.ipynb` by Tzu-Chiao Chou (credited in `analysis.py`'s docstring and the README's Authors section; keep both) (Google Colab, photo read from a Drive path, results printed and plotted), turned into a page. Used for swarming plates: one irregular colony spreading from a central spot.

On 2026-10-08 running the notebook's cell and `analyze()` on the same images gave identical plate circles, numbers, and a pixel-identical annotated image, on both the Hough and the fallback path. Don't "improve" a threshold or filter without the user: every result would change. `MIN_CIRCULARITY` is defined and unused, as in the notebook.
- **Additions agreed with the user** (2026-10-08: "你覺得需要的地方都做"): experiment fields (date, strain required; condition, incubation h, notes optional), an editable plate diameter (a result is discarded when it changes), a warning when the plate came from the fallback (`dish.method == "contour"`, where the notebook printed that Hough failed — the scale is less sure), CSV (a row per colony, full precision, CRLF + BOM) and annotated PNG export, `beforeunload` until exported. Formats are PNG, JPEG, WebP and BMP (decodable by OpenCV and previewable by a browser; not TIFF). Not done, offered and left for later: all parameters editable, intermediate images, listing rejected regions with reasons, several photos per page, a comparison chart, manual plate-circle correction or colony exclusion, HEIC.
- **Backend**: `POST /api/swarming/analyze` (multipart `file`, form `dish_diameter_mm`), a sync endpoint (FastAPI runs it in its thread pool) behind a `threading.Lock` — one analysis at a time, since a 12-MP photo holds several float copies and Render's free tier has little memory. 20 MB upload cap (413), undecodable file (400), an OpenCV failure on an odd photo (422, worded for the user, traceback logged). Nothing is stored. Error `detail`s are shown verbatim. `opencv-python-headless==4.14.0.94` (headless: Render has no GUI libraries; 4.x like Colab's; it accepts the pinned numpy 2.5.1, and pulls in nothing else).

No bridge: it takes nothing from and feeds nothing to the AHL tools.

### Backend: feature-per-folder under `app/`

Each feature lives in its own folder under `backend/app/`, containing at minimum a `router.py` that defines an `APIRouter` with its own path prefix. The router is then imported and mounted in `backend/app/main.py` via `app.include_router(...)`. There is no shared base class or plugin registry — wiring a new feature in means adding the import + `include_router` line by hand. Follow this same pattern for new features rather than adding routes directly to `main.py`.

The previous ESP32 + GY-302 version (`app/hardware_gy302/`, `/api/hardware_gy302`, and `firmware/gy302_esp32/`) was deleted and survives only in git history.

#### `app/hardware/` — prefix `/api/hardware`

A relay between the one CAPTURE-Screen device and every browser. The backend never dials the device: Render can't reach a device behind a home or lab router. Instead the ESP32 dials out to `WS /device` and keeps that socket open, and browsers only ever talk to the backend:

- `GET /status` — `{online, last_seen, device}`; `device` is the last `DeviceStatus` the firmware reported, kept after it disconnects so pages can say what went offline. `attach_device()` clears it for a new session but deliberately keeps `last_seen`, which still answers "when did we last hear anything"; the pair can't contradict itself because `device` is `None` for that window.
- `POST /read` — the hub sends `{"cmd": "read", "request_id"}` down the device socket and waits for the matching `mode: "measurement"` reply, returning the raw frames. 503 offline, 409 busy, 504 no answer within `HARDWARE_READ_TIMEOUT_SECONDS`, 502 malformed or refused by the device. **The `detail` of each is shown to the user verbatim** (pages print "Read failed: …"), so `hub.py` words the firmware's error codes — `sensor_offline` becomes "The AS7341 sensor is not responding. Check its I2C wiring." (`test_a_sensor_offline_read_says_so_in_words`) — and any new code needs the same.
- `WS /device` — the device's own connection.

`hub.py`'s `DeviceHub` holds all of it in memory, `router.py` is the thin HTTP/WS layer, and `models.py` is the contract with the firmware's JSON and `hardware_processing.js`'s validators (rename a field in all three or none). **`DeviceStatus.sensor_ok` is `bool | None`, optional on purpose**: a device still running a firmware that predates it would otherwise fail validation, and a status that doesn't validate leaves the hub with no status at all — i.e. a device that is connected but permanently "offline". `None` means "this firmware doesn't say", never "the sensor is fine". Any field added to `DeviceStatus` later needs the same treatment unless every device is flashed first. The firmware re-confirms the AS7341 on the bus every `SENSOR_CHECK_MS` and again right before every read, so `true` means "answering now", not "answered at boot" — keep it that way, or the pages go back to claiming a sensor is fine while each read returns nonsense. The live spectrum is not here: it is `app/live/`, which subscribes to `DeviceHub` as a `DeviceListener` (`on_device_changed`, `on_live`) and relays `live_start`/`live_stop` through `DeviceHub.command()`. Hardware never imports live. Rules worth preserving:
- **Online** means a device socket is attached, it has reported a status since attaching, and something arrived within `HARDWARE_ONLINE_TIMEOUT_SECONDS` (the firmware reports every 5 s).
- One read at a time (an `asyncio.Lock`). A second device connection replaces the first, which is closed with code 4000.
- One backend process (true on Render's free tier); a multi-worker deployment would need a real pub/sub instead of this singleton.
- `/device` echoes the `arduino` subprotocol that arduinoWebSockets requests. **Neither `/device` nor `/read` is authenticated yet**: anyone who finds the URL can pose as the device or trigger reads. The user deferred a shared secret (device `secrets.h` + a Render env var) to later.
- `websockets` must stay in `requirements.txt`: plain `uvicorn` can't serve any WebSocket without it, and `TestClient` doesn't need it, so the tests won't catch its absence.

#### `app/live/` — prefix `/api/live`

Live sensing: the browser side of the live spectrum, split out of `app/hardware/`. `hub.py`'s `LiveHub` keeps the connected browsers (`Viewer` outboxes), `models.py` holds `LiveFrame`, and `router.py` creates the singleton `live_hub = LiveHub(device_hub)` from `app.hardware.router`, which subscribes it at import time (so `DeviceHub.reset()` keeps listeners; tests reset both hubs).

- `WS /spectrum` — browser → `{"cmd": "live_start" | "live_stop" | "led_on" | "led_off"}`, relayed to the device unchanged (`LiveHub.set_live()` / `set_led()`), with no ack: the device's next status is the answer; `{"mode": "error", "error": "device_offline"}` when no device is attached. Server → `mode: "presence"` on connect, on every device status or disconnect, and when the device goes quiet past `HARDWARE_ONLINE_TIMEOUT_SECONDS`; every `mode: "live"` frame, to every browser.
- Presence carries exactly `GET /api/hardware/status`'s fields, because both come from `DeviceHub.snapshot()`. A device that loses Wi-Fi without closing its socket turns `online` false without any event, so the `/spectrum` poll loop calls `LiveHub.check_presence()` every tick to push that change.
- **Presence is also the keepalive.** `check_presence()` re-broadcasts at least every `PRESENCE_HEARTBEAT_SECONDS` (10 s), not only on change: with no device attached, presence is the one thing a browser ever hears, and an idle socket can be dropped by a proxy without either side noticing. `device_live.js` closes a socket that stays silent longer than `LIVE_PRESENCE_STALE_MS` (20 s, two missed beats) and reconnects. A device reporting every 5 s already is its own heartbeat, so this adds no traffic while one is online.
- **A `Viewer`'s outbox drops live frames, never presence** (`deque` of `(is_frame, text)`, capped at `VIEWER_OUTBOX_SIZE`, order preserved). `check_presence()` only resends while the online flag still disagrees, so a presence message dropped for one browser would leave it showing a state nothing corrects; frames are disposable and an offline presence must not overtake the frames before it.
- **Live is one switch, and the device owns it** (the user's choice, 2026-09-27). The device's button (GPIO 13) and every page's Live switch toggle the same `liveOn` in the firmware; the device reports it at once as `live_on` (plus `live_off_in_s`) in its status, which reaches every page as presence, so every switch shows the same state. The backend counts no viewers and decides nothing: closing or hiding a tab doesn't switch Live off. What bounds the LED's heating and bleaching of the sample is the firmware's 10-minute auto-off (`LIVE_AUTO_OFF_MS`) — keep it. `DeviceStatus.live_on` / `live_off_in_s` are optional like `sensor_ok`; `device_live.js` falls back to `state === "LIVE"` when `live_on` is missing.
- **The LED switch lives inside Live** (added in firmware 7.1.0 at the user's request, 2026-09-27): while Live is on, `led_off` keeps the stream going with the LED dark, for dark / ambient counts. The device owns it the same way (`DeviceStatus.led_on`, optional; `null` = a firmware without it) and refuses it unless Live is on; **every Live start resets it to on** (the user's choice), so nobody finds Live dark because of an earlier session. Every `LiveFrame` carries `led` (optional; `null` from older firmware, whose frames were always lit), and pages label a frame by its own `led`, never by the switch — a frame can predate the flip by one read. The button still toggles Live only.
- `/spectrum` waits on `receive_text()` with a 0.1 s timeout so one coroutine can also drain the viewer's outbox; a two-task version leaked tasks under `TestClient`'s teardown cancellation.
- `/spectrum` checks `Origin` against `CORS_ORIGINS` itself, since `CORSMiddleware` doesn't cover WebSockets. A **missing** `Origin` is rejected too (only `"*"` admits it): browsers always send one, so a connection without it isn't a browser. The check runs **after** `accept()`, and the browser is sent `{"mode": "error", "error": "origin_not_allowed"}` before the 1008 close — a handshake refused before `accept()` reaches JavaScript as a bare connection failure that no page can tell apart from a sleeping backend, and `device_live.js` would retry it forever. Adding a frontend origin (a new dev port, a wiki host) still means editing `CORS_ORIGINS`.
- `/spectrum` catches `RuntimeError` alongside `WebSocketDisconnect`: that is what starlette raises for a send on a socket that closed since the last receive, and a browser walking away shouldn't leave a traceback in Render's log.

### Config

`app/config.py` loads `backend/.env` via `python-dotenv` (silently no-ops if absent, e.g. on Render where env vars are injected by the platform) and centralizes `CORS_ORIGINS` (comma-separated) plus the hub's `HARDWARE_ONLINE_TIMEOUT_SECONDS` / `HARDWARE_READ_TIMEOUT_SECONDS`. Default allowed origins cover the GitHub Pages URL plus common local dev ports (5500, 8000). The hardware pages share a layered stack, loaded in this order after `config.js`:

- `js/hardware_processing.js` — `HardwareProcessing`, **pure functions only** (no DOM, fetch, storage, or clock — time is passed in), meant to be ported verbatim to `backend/app/hardware/`. Turns a `POST /api/hardware/read` response (`dark_1` / `light` / `dark_2` raw ADC counts) into a `Measurement`: dark subtraction (mean of the two darks, clamped ≥ 0), normalization to basic counts `raw / (gain × integration_time_ms)`, saturation at `min(65535, (atime+1)(astep+1))`, unmixing, and the stateless QC flags. Also `configFingerprint()`: a fixed-order, fixed-format hash the backend must reproduce exactly. `toMeasurement()` throws for anything whose `mode` isn't `"measurement"`, so live-stream frames can never be stored or fitted.
  - **`signalId(basis)`** names what `fluorescence` is (today `"F4"`, from `config/unmix_basis.json`). Every Measurement, run and curve carries it as `signal`, and a curve only converts readings with the same signal. This is the hook for changing the signal definition once real data says how (F4/F3, OD normalization, a measured unmixing basis): add a method, and old curves keep saying what they were fitted on instead of silently converting a different kind of number.
- `js/curve_fit.js` — `CurveFit`, pure functions: weighted 4PL fit, LOD/LOQ, usable range, inversion with a delta-method 95% CI. Shared by `hardware_local.js` and `plate_assay.js`; loaded before `hardware_local.js` on every hardware page.
- `js/hardware_local.js` — browser-local storage of runs (`plans`), curves and measurement batches (fitting and inversion through `CurveFit`), and the blank-scatter baseline for `HIGH_SCATTER`. It is the temporary persistence backend. Its key is `lasreader.hardware.local.v3`; on load it deletes the v2 store and the v1/simulated-device keys — the user chose to clear v2 data rather than migrate it (2026-09-27; it held no real data).
  - **Manual datasets.** `createManualDataset()` stores CAPTURE-Screen readings recorded earlier and typed in at Calibrate as a run with `source: "manual"`. Source and Set up take only the source, conditions, date and config; the values are entered at step 3 (Enter values, which opens once Set up is complete), and its Create run stores the whole dataset at once — no run exists until then, so there is never a half-entered manual run. The result is a run, every slot already filled, so Fit, exclusions, and saving run unchanged. Rows keep their entry order as slots. What wasn't recorded stays `null` (`fluorescence_sd`, `scatter`, `raw`), and `timestamp_utc` holds only the `measured_on` date. Such a run can't be re-read (`recordPlanMeasurement` refuses it; step 3 then shows the entered values as done). It binds to the instrument's current config or a config typed in field by field (`HardwareApi.fingerprintConfig()`), and its values are taken to be the current signal's. Runs and curves carry `source`, and Calibrate and Curves show it.
  - **Weights without read noise.** When no point has a read-noise SD and replicates give no spread, `fitCurve` fits unweighted and takes the inversion CI's reading variance from the residuals.
  - **A saved curve never changes** (`saveCurve()` refuses an id already saved): batches refer to it by id, and what they converted has to stay reproducible. Refitting a run with other exclusions makes another curve; the run lists all its curves.
  - **Measurement batches.** `createBatch()` needs the instrument online, its config equal to the curve's, and the current signal equal to the curve's. `recordBatchReading(role "blank" | "sample")` stores each tube **the moment it is read**, before anything is drawn. A tube read under another config or signal is still stored but left out automatically with that reason (and `STALE_CONFIG`), and can't be counted back in; any other tube can be left out only with a reason, and stays in the batch and the export. Each sample's `InverseEstimate` is the **mean of its counted tubes converted once**, with the reading variance divided by n (the curve's parameter covariance is not, since every tube shares it); `blank_estimate` does the same for the blanks, and Measure warns when the blank mean converts to anything but "below LOD". Estimates are stored as computed and recomputed only when that group's tubes change, always against the batch's own curve; the batch also keeps a `curve` snapshot (conditions, signal, config, LOD/LOQ, range) so an exported row reads without the curve. Batches are capped at `LOCAL_BATCH_LIMIT` (60) because `localSave()` swallows a `QuotaExceededError`; making room drops the oldest **exported** batch and refuses when none is — a batch that exists only here is never dropped. `exported_at` is cleared whenever a tube changes after an export.
  - **Backup: `exportBackup()` / `importBackup()`, on the Data page.** Runs, curves (with their `curve_private`) and batches go in **one file** (format `lasreader.hardware.backup`, version 2), and there is exactly one place to export and import it: forgetting one of several downloads used to leave a curve whose calibration data was gone. Version 1 files (the earlier workflow, without conditions) are refused with a message saying why. `blank_scatter` is deliberately left out: it is derived state that the next blank re-establishes, and restoring a stale one would flag good samples as `HIGH_SCATTER`.
    - An imported file is **untrusted** — hand-edited, from another build, or not ours at all. `localPlanProblem()` / `localCurveProblem()` / `localBatchProblem()` (sharing `localMeasurementProblem()` and `localEstimateProblem()`) check every field a later calculation touches, because a bad entry goes on converting real readings into wrong concentrations. Sections import independently: one bad curve must not cost you the runs in the same file.
    - Rules that hold everywhere: **an id already stored is skipped, never overwritten** (what is here was produced on this machine; the file is a copy of something older), and **everything rejected is reported with its reason** — a restore that quietly drops an entry leaves nothing on screen to show the gap. A curve whose `private` block is missing or not 4×4 is rejected rather than stored: `localInverseCore()` reaches straight into `cov` / `noise` and would throw on the first conversion. Plan items are re-sorted by `slot`, and duplicate slots rejected, or `targetItem()` and `recordPlanMeasurement()` would disagree about which tube is next. `measurement.raw` is checked loosely (every value finite) — nothing computes from it.
  - **Reset: `resetAll()` / `resetPreview()`, the Reset card on the Data page.** Deletes everything the software stores in the browser, irreversibly. Four things are load-bearing, and each was found by testing rather than assumed:
    - **The memory copy must be cleared too.** `localLoad()` falls back to `localMemoryStore` whenever the key is missing, so removing only the localStorage key **resurrects the deleted data on the very next save** (tested: a naive delete brings the marker straight back). `resetAll()` nulls it first, and a `storage` listener does the same in every *other* open tab — otherwise a second tab's stale copy would write the whole store back. The listener ignores events for unrelated keys.
    - **It matches on the `lasreader.` prefix, never a list of names**, so a key added later can't be left behind. The prefix includes the dot: an origin's storage is shared with everything served from it (igem-ncku-software.github.io hosts more than this site), and a look-alike such as `lasreaderX.` must survive.

It runs no HTTP server. It keeps one outbound `WebSocketsClient` to `BACKEND_HOST` + `/api/hardware/device` and speaks the protocol above: status on connect, on every change, and every 5 s; frames back to back while Live is on; and `read` answered with one dark → light → dark measurement (integer raw counts) tagged with the `request_id`, or `error` `busy` / `sensor_offline`.

It is **one file, `capture_screen.ino`, plus the gitignored `secrets.h`** — the user asked for it that way on 2026-09-27 after a brief split into modules, so don't split it again. It has numbered sections, each opening with its own rules:
1. **Configuration** — every constant: identity, pins, sensor defaults, timing, `LIVE_AUTO_OFF_MS`. Above it, **the include order is load-bearing**: `WiFi.h` / `ArduinoJson.h` / `WebSocketsClient.h` first, then `DFRobot_AS7341.h`, then `#undef ERR_OK` — DFRobot's `#define ERR_OK 0` would otherwise turn lwIP's `ERR_OK = 0,` into `0 = 0,`. `Frame` and `DeviceState` are defined before the first function, or Arduino's auto-generated prototypes can't see them.
2. **Sensor** — the AS7341. `sensorOk()` (`sensorPresent`) means "answering now": the ACK is re-checked every `SENSOR_CHECK_MS` and before every read, never judged from the reading (a dark cuvette reads 0). Gain is a register index; the multiplier is derived from it, never a second constant.
3. **Button** — a FreeRTOS task on core 0 samples GPIO 13 every 5 ms and counts debounced presses (30 ms) in one counter. It has to be a task: a live frame blocks `loop()` for ~0.5 s and a measurement ~1.6 s, long enough to miss a press. A button held at boot is not a press. **Only short presses exist** (the user's choice); the button does nothing but toggle Live.
4. **OLED** — status only: `oledOk` comes from an I2C ACK plus `begin()`, and every draw returns early without it, so a loose display wire can't stall a read. A status bar (Wi-Fi RSSI, backend, state) over one body chosen by priority: a 2 s notice, measurement progress (Dark 1 / Light / Dark 2), sensor fault, the live bar chart (F4 filled, others outlined, F4 count and the auto-off countdown; the website's y-axis rule from `LIVE_Y_BASE_COUNTS`), or the idle summary (connection, IP, gain/integration, last read's raw light F4). Only `displayService()`, `displayMessage()` and `displayMeasureStep()` draw — the rest only record, so they are safe inside `ws.loop()`. `displayMeasureStep()` draws before the LED switches on, so it adds no LED-on time. The SSD1306 driver raises the bus to 400 kHz for its own transfers and restores 100 kHz.
5. **Backend link** — Wi-Fi (non-blocking: `setup()` waits at most 10 s, then `linkService()` keeps trying, so a bad password never bricks the sketch) and the JSON protocol. `addConfig()`'s formatting is part of the fingerprint contract: `led_current_mA` as a fixed 3-decimal string and an integer gain as an integer, because the browser hashes `Number(...).toFixed(3)` and `String(gain)`.
6. **Controller** — the state machine (IDLE / LIVE / MEASURING) and the **only code that writes `LED_PIN`** (`ledSet()`). Web commands (from `ws.loop()`) and button presses only *record*; `ctrlLoop()` applies them in order, so the button and the web can't both drive the LED. It owns the Live switch (`setLiveOn()`, which both inputs go through): every request marks the status dirty, **even a refused or redundant one**, because the page that asked has already flipped its switch and needs the device's answer. Switching Live **on** is refused during a measurement or without the sensor; **off** is always accepted. A button press during a measurement is dropped with a "Busy" notice rather than queued. Live survives a backend disconnect (the OLED is a viewer too); a lost sensor switches it off. LIVE follows the switch whenever no measurement runs, so a read preempts streaming and streaming resumes on its own. The LED switch within Live is `ledWanted` (`ctrlWebLed()`, web only, refused unless Live is on, reset to true by `setLiveOn(true)`); `syncLive()` applies it through `applyLiveLed()` **between reads only** and restarts the settle wait (`LIGHT_SETTLE_MS` / `DARK_SETTLE_MS`), and `liveLit` — what the LED did for the whole read — is what each frame's `led` reports and what the OLED labels "dark". `ctrlPump()` (link + status, plus button presses while measuring) runs between the two SMUX cycles of every read, so the pong doesn't time out mid-measurement.
7. **Serial diagnostics** (115200) — `?` settings, `i` I2C scan, `b` button level, `l` LED toggle (refused unless IDLE with Live off), `d` dark/light table (claims MEASURING via `ctrlClaim()` so neither a web read nor Live can take the LED), `g`/`t`/`s` sensor settings (a status goes out at once, since they feed the fingerprint). Commands are shape-checked: one letter, or a letter plus digits only.
8. **setup / loop.**

Other rules:
- The config fingerprint is LED current, gain, ATIME, ASTEP and `BUILD_ID`. **There is no firmware version anywhere** (the user's choice, 2026-09-27): first it was taken out of the fingerprint, because bumping it staled every curve even when the reading path hadn't changed; then the whole feature was deleted — the constant, the `firmware_version` field in status and measurement messages, `DeviceIdentity.firmware_version`, the Instrument and Measure rows, and the OLED/Serial boot lines (both show `BUILD_ID` now). Don't add a version back without asking. When a change alters the reading path, stale the curves on purpose by changing `BUILD_ID`; the user will revisit the fingerprint's fields case by case. A device still running 7.1.0 or earlier sends `firmware_version` anyway; pydantic and the browser ignore unknown fields, so it stays online (`test_a_firmware_that_still_reports_its_version_stays_online`). Deploy order for a removed field is always backend and frontend first, then flash.
- `LED_PIN` is 25 on this build, not the reference design's GPIO 2. LED current is 5.553 mA, the safe-start value measured on 2026-08-25; it is a constant the firmware cannot read back.
- `BACKEND_HOST` / `BACKEND_PORT` / `BACKEND_USE_TLS` default to the Render backend and are wrapped in `#ifndef`, so `secrets.h` can point the device at a local backend. Wi-Fi credentials go only in `secrets.h`, which is gitignored — copy `secrets.h.example`.
- TLS skips certificate validation: with no CA or fingerprint, WebSockets 2.7.2 calls `setInsecure()` on ESP32. `beginSslWithCA()` is how to pin Render's root certificate later. Its handshake sends `Origin: file://` and `Sec-WebSocket-Protocol: arduino`, which is why `/device` has no origin check and echoes the subprotocol.
- Serial Monitor prints `[wifi]` / `[backend]` connection events and a "still connecting" line every 10 s — the first place to look when the device doesn't appear online.

- `js/config.js` — defines `BACKEND_BASE_URL`, branching on hostname (`localhost` / `127.0.0.1` → `http://127.0.0.1:8000`, else Render). Because there's no build step there's no way to inject this at build time, so it's a runtime check kept in one file. **Must be loaded before every other script.**
- `js/plate_assay.js` (plate-assay.html) — the Plate Reader Assay (see above).
- `js/swarming.js` (swarming.html) — the Swarming Assay's page: upload, show, export; keeps its own small helpers like `plate_assay.js`.
- `js/hardware.js`, `js/hardware_calibration.js`, `js/hardware_curves.js`, `js/hardware_measure.js`, `js/hardware_data.js` — one per hardware page, in step order. `sensorReading()` lives in `hardware_common.js` and is the single rule for `sensor_ok`: **every page that reads blocks on it** — Instrument (the self-check), Calibrate (where a dead sensor outranks "every tube has been read" in the same `#plan-read-reason`), and Measure (`readBlockReason()`, shared by the Blank and Samples reads); the step bar shows "Sensor fault" on step 1. Instrument also shows it as its own node on the signal path and in the verdict, so a connected device with a dead sensor never reads as ready. `null` (a firmware older than the field) is shown as "Not reported" and blocks nothing — that is the state every device was in before, and a failed read still explains itself. Each page re-applies the block from the status fetched alongside (or, on Instrument, right after) a read; a *failed* read says nothing about the sensor, so it leaves the button usable for a retry.
  - **Instrument (`hardware.js`)** was reorganised on 2026-09-27 at the user's request, aiming at a page that makes the device's condition clear at a glance: two cards, "Status" and "Self-check", with short text. The user wants the page concise **but keeps the full "Current configuration" table, because this is iGEM software** (a cut to a one-line config row was reverted the same day). It polls `getDeviceStatus()` every `DEVICE_STATUS_POLL_INTERVAL_MS` (a sequence number drops a response overtaken by a newer one). `linkState()` names the first link that failed — `checking`, `unreachable` (the error's `backendUnreachable`), `backend-error`, `offline` (`deviceOffline`, with `lastSeen`), `invalid` (`deviceInvalid`), `online` — and everything else is derived from it:
    - **The verdict** (`#status-verdict`, `instrumentVerdict()`): connection and self-check status, not overall measurement readiness. Connection errors and sensor faults take priority, followed by this page's self-check in progress and other MEASURING activity. An online reader then shows "Connected · Self-check not run", "Self-check incomplete", "Self-check needs attention", "Self-check passed", or "Connected · Repeat self-check" after a config change. A pass explicitly covers stable dark readings and unsaturated light channels; LED response is not verified. `lastSelfCheck` holds the latest completed check and its config fingerprint; `lastSelfCheckError` holds a newer incomplete attempt until another check completes. A failed retry never restores an earlier pass. `lastPassedSelfCheck` retains the previous passing time as labelled history with its config, shown alongside a failed/incomplete retry. These are page-session state only. Counts are grouped with `toLocaleString("en-US")`, for the same reason times use a fixed format.
    - **The signal path** (`.hw-path`): Backend → CAPTURE-Screen, which then **forks** to the AS7341 sensor and the excitation LED — drawn as a fork because that is how it is wired (the ESP32 drives both); a straight chain would have put the LED behind the sensor. Each node has a dot, a value and one line; a link is accent while it answers, dashed error where it breaks, and a plain hairline past the break, where the nodes say "Unknown" with the upstream cause ("Device offline", "Backend unreachable"). The sensor node's word is `sensorReading().text`, the shared rule. The LED node carries what the old State tile did (Off · Idle, On · Live with auto-off, Measuring · Dark · light · dark). Below 720 px it stacks, links turn vertical, and the sensor and LED sit side by side.
    - Then the Current configuration table. That table (`.spec-table`) is a datasheet — Parameter | Value | Note, the structure of the wiki's hardware tables (`hw-table`, "Quantity | Measured | Note") in this site's table material — for the user's "clear, intuitive, and professional for iGEM": LED current, gain, ATIME / ASTEP, integration time, full scale, build ID, config fingerprint, device ID, Wi-Fi, uptime, each with a short note saying where the value comes from (the two formulas are `HardwareProcessing`'s own; keep them in step). Only the Note column wraps, so it fits a phone without sideways scrolling. It is hidden while the status is unavailable, never left showing an old config, and re-renders only when a value changed.
  - **One self-check replaced the Dark read and Blank read buttons**: both were the same `POST /read` (dark → LED on → dark), and the old "Dark read" claimed the LED stayed off. Blocked while offline, on a sensor fault, or while MEASURING. **Keep it simple — the user's words: "clear and to the point"** (2026-09-27: a version with a four-check list in the intro, a "why" on every step and a card per result was judged too complex). So: one sentence saying it checks dark stability and saturation, two numbered steps (`.procedure`: insert a cuvette with buffer only, close the lid — the button is the third step), then one result line and a four-row list. The result line says which checks passed, or what failed, with the time and advice. A read error says "Self-check incomplete". The list (`.check-list`) is one row per check: Dark stability (largest Dark 2 − Dark 1, limit shown), Peak signal (brightest light reading as a share of full scale), Dark level (highest dark reading), Light − dark (largest light minus mean dark, unclamped, over the darks it has), each with a Pass / Fail / Info chip. One short note explains that Dark level and Light − dark are informational and LED response is not verified. `HardwareProcessing.toSelfCheck()` keeps the three frames and never makes a Measurement. The full five-row raw-count table stays behind a "Raw counts per channel" `<details>` — data is never dropped from this page. With no signal shown there is no basis note. **The absolute dark level is shown because the difference can't see a steady light leak** (both darks rise alike). Only Dark stability (±`DARK_DRIFT_TOLERANCE_COUNTS` = 2 counts) and Peak signal (a channel at full scale is saturated) are graded, once, in `analyzeSelfCheck()`, which both the result line and the list read — so they can't disagree; Dark level and Light − dark are "Info" — **the user's choice until a baseline has been measured on the real instrument, so don't invent thresholds for them**. First real run, 2026-09-27: drift 0, peak 0.5 % of full scale, darks 0, light − dark +271 counts.
  - Removed on purpose, don't add back: the 60-min "run a dark read" reminder and its key (no step depends on it; every measurement subtracts its own darks), the "Curves matching this config" count (the step bar's "N usable" already says it, with the signal check this one lacked), the always-empty Emission filter row (`emission_filter` stays in the `HardwareConfig` contract), the per-second heartbeat ticker, the three status tiles (replaced by the verdict and the signal path), the self-check's F4 / F3 tiles and basic-count row, and the session log (the user removed it on 2026-09-27).
- `js/backend_status.js` (every page) — polls `GET /health` every 12s for the footer badge. It reports whether the backend is up, not whether any hardware is.

CSS is one file, `css/style.css`, with a `:root` variable palette matching the team wiki. JS-generated elements are styled by class name (`.status-message.success` / `.error`, `.result-block`, `.chart-note`, `.predict-form`), so renaming a class means changing both files.

### Deployment

`.github/workflows/deploy-pages.yml` uploads the entire `frontend/` folder as a GitHub Pages artifact on every push to `main` — no build/transform step runs, so new files under `frontend/` are picked up automatically. Backend deployment to Render is external to this repo (no Render config file present here).
